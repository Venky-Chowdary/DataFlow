## Production root cause (QA)

On production the Transform step has no nodes because the canvas is not mounted.

QA’s evidence, checked against this tree:

- `studio_canvas` defaults to `False` (`apps/api/services/workspace_store.py` 21). Absent or false keeps the wizard (`workspace_store.py` 18–19).
- Transfer passes that combined flag through as `canvasEnabled={studioFlags.canvas}` (`apps/web/src/pages/TransferPage.tsx` 7750).
- The prop defaults to false (`apps/web/src/pages/transfer/TransferTransformStep.tsx` 146: `canvasEnabled = false`).
- With the flag off, the step renders the legacy section. The add-a-step form is `TransformStepBuilder` at `TransferTransformStep.tsx` 849–856, inside `{showBuilder && (…)}`. That form is a catalog picker. It has no node objects, no palette, and no drag-and-drop.

The canvas component is the other branch (`TransferTransformStep.tsx` 644). Production does not take it while `studio_canvas` is false. A browser opt-in alone does not override that: `resolveStudioFlag` requires the server flag as well (`apps/web/src/lib/studioFlags.ts` 17–18). Local measurement of flags-off matches QA: `legacyList: true`, `canvas: false`, `nodeCount: 0`, `opCount: 0` (`transform-flags-off-1440x900.png`).

The flag-on findings later in this review describe the surface operators will get after the owner turns the gate on. They are not what production renders today.

### How the canvas should reach users

The owner decides. This change does not edit production config, and it does not change the default in `workspace_store.py`.

**Recommendation: keep the default off, and turn the existing Settings gate on only after the canvas is ready.**

Settings → General already has the control. The checkbox is “Recipe canvas” (`apps/web/src/pages/SettingsPage.tsx` 777–791). Save calls `updateWorkspaceSettings` with `studio_canvas` (`SettingsPage.tsx` 498–504), which writes `data_dir()/workspace.json` (`workspace_store.py` 12, 79–84). The same save writes `df.studioCanvas=1` in that browser (`SettingsPage.tsx` 510–512). Other browsers stay on the step list until they save here too, because both sides of `resolveStudioFlag` must be true. The hint under the checkbox already says that.

That gate is one file for the deployment. `get_workspace_settings` does not take a workspace id, so two workspaces on one API share the flag. A true per-workspace-id switch would be a new store key. It is the right shape if one customer must see the canvas while another stays on the step list. It is not required to reach the operators on this production deployment: the Settings checkbox already does that, and only an admin with `workspaceManage` can save it (`SettingsPage.tsx` 104–112).

Turning the code default to `True` would put every new and existing deployment on the canvas the moment the browser also opts in, including deployments that have not asked for it. The canvas is not ready for that: with the flag on, the palette starts hidden, drag is limited to executable operations the operator is allowed to edit, and the recipe is memory-only (next section). Ship those, then the owner checks “Recipe canvas” and saves. Until that save, production keeps the legacy builder.

## 2. Architecture verdict

The flag gate is sound. The layout and CSS strategy needs a rework before more Transfer chrome is added.

**Keep.** Server flag plus browser flag, default off, failed settings stay off, classic tree unchanged when either side is off. That is the right safety boundary, and the three measured states confirm it. The recipe (`shapeSteps`) as the only source of canvas nodes is also the right engine boundary: the graph must not invent steps the transfer will not run.

**Change.**

1. The “one shell” is only the Transfer page, and only when `studioFlags.canvas` is true (the comment at `studio-next.css` 1338). Overview, Connectors, Contracts, Jobs, Schedules, Transforms (post-load SQL), Query, Settings, and the rest of the nav stay on the classic app. There is no Datasets screen (`DataTransferApp.tsx` 76–90). Flags-on Transfer is edge-to-edge. Every other screen is the older inset layout. That is two products.

2. CSS is two cascades fighting. Classic layout is locked with `!important`. The new file is not allowed to use `!important`, so every later classic override must remember `:not(.is-studio-next)` or it lands on the new page. The structure rules at `transfer-studio.css` 11767 do that today. Rules added so an overlap checker would not count ellipsis as clipping (`overflow: visible`, `overflow-wrap: anywhere`) made the checker pass and made the table and the route bar worse.

3. The canvas is mounted as a closed overlay. The palette is `display: none` at desktop, the empty recipe draws nothing, and the tests open the palette before they look. An operator who turns the flags on sees a blank stage.

### Rework, when UI-001 and UI-002 are fixed

Do this as one layout pass, not another patch on `studio-next.css`.

- **One shell.** A single full-page frame (top bar, sidebar, content, one 48px bottom bar) used by every full-page surface. The flag still chooses classic vs shell. The shell is not a Transfer-only class.
- **Tokens.** Space, type, color, and the z-index scale in `tokens.css` stay the only primitives. Feature CSS does not add a second scale or raw colors.
- **Scoped CSS.** Shell rules live in one stylesheet that does not have to out-specify classic `!important`. Classic locks that must not apply to the shell carry `:not(.is-studio-next)`, including the structure-card block at `transfer-studio.css` 11767. Tables scroll on the x-axis (`overflow-x: auto`, `white-space: nowrap`). Route labels truncate inside the bar.
- **Canvas boundary, ready for the transform engine.** The palette is a visible dock whenever the canvas is on. Drag sources stay hittable. The stage is the drop target and fills the shell. An empty recipe shows that target and zero nodes; it does not hide the palette. Properties sit in their own region and do not share a box with the palette. Nodes still come only from `shapeSteps`. Operations the engine cannot run stay visible and disabled.

## Drag gate and recipe persistence (flag on)

These apply after the owner turns `studio_canvas` on. They do not change what production shows while the flag stays off.

### What can be dragged

`canEdit` is `canPlan && !syncRefused` (`TransferTransformCanvas.tsx` 215). A palette button is draggable only when that is true and the catalog marks the operation executable:

```778:779:apps/web/src/components/transfer/TransferTransformCanvas.tsx
                      draggable={canEdit && operation.executable}
                      disabled={!canEdit || !operation.executable}
```

`beginAdd` returns immediately when `canEdit` is false, and it refuses a spec with `executable: false` (`TransferTransformCanvas.tsx` 325–331). Planned operations render in “Not executable yet” as disabled buttons with `data-executable="false"` and no drag handler (`TransferTransformCanvas.tsx` 810–825). `executableRecipe` then keeps a non-executable node out of the program the row engine runs, and blocks every step that depends on it (`canvasDocument.ts` 510–518).

So a viewer, a refused sync mode (CDC, SCD2, mirror), or a planned operation (join, lookup, and the rest of the set family until the catalog says executable) cannot produce a node. That is the correct engine boundary. The empty production page is still the flag, not this gate: the gate never runs while `canvasEnabled` is false.

### Where the recipe lives today

`shapeSteps` is React state, initialized to `[]` (`TransferPage.tsx` 358). A fresh transfer assigns `[]` again (`TransferPage.tsx` 6202). Reload, a new tab, or “New transfer” drops the graph. `CanvasDocument` (`canvasDocument.ts` 36–39) adds viewport and selection on top of those steps, and that document is not written anywhere.

The wire the engine already accepts is sent only when a plan or a run is submitted. `recipePayload` returns `{ steps }` when at least one step is enabled, and `undefined` otherwise (`shape.ts` 504–506). Execute and the schedule stamp persist that payload:

- A run carries `shape_recipe` and `approved_shape_recipe_hash` (`TransferPage.tsx` 5677–5678). The hash is the canonical identity of the enabled steps (`shape_models.py` 401–406). Disabled steps are outside the hash. An empty recipe has no hash.
- A schedule stores `shape_recipe` and `approved_shape_recipe_hash` (`schedule_store.py` 206–207) and replays them on the next run (`schedule_runner.py` 441–446).
- `set_graph` is a separate identity (`set_hash`). `recipe_hash` ignores it (`shape_models.py` 23–26). The client `ShapeRecipeWire` is `{ steps }` only (`shape.ts` 26–28), so the canvas does not send a graph today.

There is no draft between those two moments. An operator who builds ten steps, previews them, and refreshes before Execute or before saving a schedule has no recipe to restore.

### Persistence design

One document, two parts. Do not invent a second recipe format.

**Program.** Persist `ShapeRecipe` as the API already parses it: `steps` plus optional `set_graph`. Validate on write with `ShapeRecipe.parse`, the same function preview and Execute use. Store the `recipe_hash` returned by that parse next to the document. On load, parse again and refuse to treat the draft as approved when the stored hash does not match. Approval stays the existing rule: Continue / Validate pin `approved_shape_recipe_hash`, and Execute refuses a mismatch. A draft hash is not an approval.

**Presentation.** Persist viewport, selection, and node positions beside the program, under a key the hasher ignores (`canvas_layout`). Restoring a layout must not change `recipe_hash`. If the layout is missing or refers to a step index that no longer exists, drop it and fit the chain. Palette open/closed is presentation too; the default after the UI fix is open, and the saved bit only records the operator’s last choice.

**Where it is stored.**

| Moment | Store | What is durable |
| --- | --- | --- |
| Editing, before approval | Transfer draft on the workspace, keyed by source identity + destination identity + the operator’s draft id | `steps`, `set_graph` if any, `recipe_hash`, `canvas_layout` |
| Approved, before Execute | The same draft, with `approved_shape_recipe_hash` set to the parsed hash | Execute reads this. A later edit clears the approved hash until preview balances again. |
| Execute | The job record, as today | The run is reproducible from the job. The draft remains for the next edit. |
| Schedule save | `schedule_store` fields that already exist | Unattended runs keep at-least-once upsert unless a schedule has proven otherwise. The draft is not a second schedule. |

The draft is server state, not `localStorage`. A second browser of the same operator reloads the same recipe. A failed save stays on screen with the error; the in-memory steps are not cleared. Quarantine and row fidelity are unchanged: persistence stores the program, and the engine still refuses to run a step the catalog marks non-executable.

**Load rule.** On entering Transform, if a draft exists for this source and destination, restore `shapeSteps` from the parsed steps and the layout from `canvas_layout`. If none exists, start from `[]` and an open palette. “New transfer” archives or deletes that draft explicitly (`TransferPage.tsx` 6202 is the clear point) so a new route does not inherit the previous recipe.

**What not to persist.** Undo stack, in-progress inspector drafts that were never committed to `steps`, and preview rows. Those are session state. The sample preview is recomputed from the restored recipe.

This design is not implemented in this commit. The default flag stays `False`.

## What this does not change

The production default stays off. Production `workspace.json` is not written by this change. Flags-off classic UI is untouched. No UI-001 or UI-002 code is in this review.
