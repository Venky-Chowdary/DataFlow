# Structural attestation — live PostgreSQL and MySQL evidence

A row-perfect load can still hand a client an unusable table: no primary key, a
dropped unique constraint, a missing foreign key, an index the application plans
against, a NOT NULL that became nullable, a lost default, or an identity counter
still pointing at 1 so the first application insert collides with a migrated row.
None of that is visible to a row count or a checksum — the defect lives in the
destination catalog, not in its data.

`services/physical_state_diff.py` reads that catalog back after the write on its
own connection, and `services/identity_watermark.py` proves the generator. This
document records what they actually reported against live engines.

## Harness

```
apps/api/scripts/live_structural_attestation_matrix.py
artifact: /home/ubuntu/repro/structural_attestation_results.json
```

Source (PostgreSQL, port 5433), carrying every guarantee at once:

```sql
CREATE TABLE attest_parent (id BIGINT PRIMARY KEY);
CREATE TABLE scn_src (
    id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email     VARCHAR(64) NOT NULL UNIQUE,
    parent_id BIGINT REFERENCES attest_parent(id),
    status    VARCHAR(16) NOT NULL DEFAULT 'active',
    CONSTRAINT scn_src_status_ck CHECK (status <> '')
);
CREATE INDEX scn_src_status_idx ON scn_src (status);
-- 20 rows, then setval(..., 20, true)
```

Two destination shapes per engine: a create-new destination, and a destination an
operator pre-created by hand from a column list only.

## Measured result (4 scenarios, 2 engines)

| engine | destination | PK | unique | FK | index | not null | default | check | identity |
|---|---|---|---|---|---|---|---|---|---|
| postgresql | create-new | carried | carried | carried | carried | carried | carried | carried | verified, next 21 |
| postgresql | hand-written, no guarantees | absent | absent | carried¹ | absent | absent | absent | absent | unverified (`id`) |
| mysql | create-new | carried | carried | carried | carried | carried | carried | carried | verified, next 21 |
| mysql | hand-written, no guarantees | absent | absent | carried¹ | absent | absent | absent | absent | unverified (`id`) |

¹ Foreign keys are added after the load by `services/foreign_key_carry.py`, which
an existing table accepts — the `ALTER TABLE … ADD CONSTRAINT` also validates the
rows just written, so a carried key is proof the destination holds no orphans.

The hand-written rows land and every checksum matches; the attestation is the only
thing that tells the operator the table is not the source's table. Nothing there is
reported green, and `verified: false` blocks the certificate.

MySQL create-new, read back with `SHOW CREATE TABLE`:

```sql
CREATE TABLE `scn_dst` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `email` varchar(64) NOT NULL,
  `parent_id` bigint DEFAULT NULL,
  `status` varchar(16) NOT NULL DEFAULT 'active',
  PRIMARY KEY (`id`),
  UNIQUE KEY `email` (`email`),
  KEY `scn_dst_scn_src_status_idx` (`status`),
  CONSTRAINT `fk_scn_dst_parent_id` FOREIGN KEY (`parent_id`)
      REFERENCES `attest_parent` (`id`),
  CONSTRAINT `scn_dst_chk_1` CHECK ((`status` <> _utf8mb4''))
) ENGINE=InnoDB AUTO_INCREMENT=21
```

## Two defects this run found and fixed

1. **A carried CHECK was reported as dropped across engines.** PostgreSQL stores
   the predicate as `status::text <> ''::text`, MySQL as `` (`status` <> _utf8mb4'') ``.
   The comparison now strips casts and charset introducers outside string
   literals, so an equivalent predicate compares equal while a genuinely
   different literal (`'a::b'`) still differs.
2. **A carried generator was reported as a lost default.** PostgreSQL records it
   as an identity or a `nextval` default; MySQL records `AUTO_INCREMENT` with *no*
   column default at all, so reading only `default` marked every faithfully
   migrated identity column as a dropped default. The generator's own health
   (next value past the migrated maximum) stays owned by `identity_watermark`.

## Scope — what this does not prove

Local PostgreSQL and MySQL only, single table, 20 rows. It does not prove Oracle,
SQL Server, Snowflake or lakehouse destinations, multi-table dependency ordering
at volume, or partitioned/clustered index carry.
